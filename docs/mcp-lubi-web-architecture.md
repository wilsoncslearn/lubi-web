# Lubi 单用户前后端项目：架构与迁移设计

状态：设计草案，未实现。目标目录为当前项目根目录。此项目独立于原 Obsidian Vault；本阶段不修改原插件、不访问个人数据、不部署、不导入。

## 1. 决策与边界

- 用户：仅一人；需登录，不能因为“只有自己使用”而公开 API。
- 第一阶段：独立 Web 数据库；原插件与 Vault 保持原样。先做合成数据可运行的最小系统，再做手动、单向、可预览导入。**不做双向同步**，不能把 Web 中的更改自动回写 Vault。
- Web 的数据源是服务器数据库；原 Vault 仍是原插件的数据源。两边数据并不实时一致，应在界面明确标注。
- 首版范围：登录、项目/任务、每日时间记录、简单的日/周统计、备份导出。日历/甘特、复杂重复规则和回顾逐步加入；AI、插件自更新、后台工作流和在线同步不在首版承诺范围内。

## 2. 原项目核对依据

- `../obsidian_task_kanban/插件源码/lubi/src/core/tasks.ts`：schema v14 的 `TaskStore` 含 `tasks` 和可选 `projects`、`projectContainers`；任务有 ID、项目/父级、日期/起始时间、预计分钟、重复规则、完成/跳过日期、状态及其他可选字段。
- `../obsidian_task_kanban/插件源码/lubi/src/core/records.ts`：`Rec` 包含日记日期、开始时间、实际分钟、预计快照、分类、标题、关联任务、支出与额外字段；解析器只识别特定形状的 Markdown 列表行。
- `../obsidian_task_kanban/插件源码/lubi/src/services/taskStore.ts`、`../obsidian_task_kanban/插件源码/lubi/src/services/journal.ts` 是依赖 Vault 的读写边界；不能原样用于服务器。
- 源码 `package.json` 和 `manifest.json` 标示 1.8.0；原仓库有未提交的改动。这里的方案依据静态阅读，未运行构建/测试，也未接触真实数据。

## 3. 推荐技术结构

```text
lubi前后端项目/
  apps/web/          React + TypeScript + Vite；单页应用，移动端自适应
  apps/api/          Node.js 22 + TypeScript + Fastify；同源 /api 路由
  packages/domain/   与平台无关的模型、校验、日期/重复/统计计算
  packages/db/       SQLite schema、迁移脚本和数据访问层
  docs/              决策、导入映射、部署与恢复说明
  deploy/            可选的服务进程与反向代理配置（不要求容器）
```

优先把现有 `src/core` 中真正无 Obsidian 依赖的函数以明确许可及版本来源复制/抽取到 `packages/domain`，保持行为测试；不要把原 `src/ui` 或 Vault 服务文件直接拷贝为 Web 实现。若希望长期共享源码，再单独规划两仓库间的包发布或工作区迁移，避免偷偷依赖原仓库的相对路径。前端通过同源 `/api` 请求后端，后端独占数据库与凭据；浏览器不直连数据库。

## 4. 数据模型初稿

- `users`：单账户 ID、登录名、强口令哈希、创建时间。所有业务数据保留 `user_id`，为授权检查与备份明确边界。
- `projects`：沿用原项目 ID（导入时）、标题、创建时间及未识别字段的保留策略。
- `tasks`：保留原任务 ID、用户归属、项目/父级、状态、排期与预计、排序、版本号；复杂的重复规则、完成日、后台字段及未知字段可先以经过严格验证的 JSON 文本保存，并在迭代时拆出索引字段。保留 `origin` 和历史关联，不能因 UI 暂不支持就丢弃。
- `records`：新增 Web 内部稳定 ID；保留日期、开始、分钟、预计快照、分类、标题、原任务 ID、备注、金额、额外字段与原始导入信息。实际分钟与预计快照分开统计。
- `import_batches` / `import_items`：文件摘要、格式版本、来源、预览结果、应用时间、项目/任务/记录映射与冲突信息；保证相同文件重复导入可识别。不要只靠标题+时间作为全局唯一键。
- 时间字段约定：排期日/日记日为本地日历日期，时刻为本地 `HH:mm`，审计时间为 UTC 时间戳；默认时区由部署配置明确指定，不能依赖浏览器/服务器碰巧相同。
- 数据库迁移必须版本化；API 更新使用事务及版本号/冲突响应，不以最后写入无条件覆盖。

## 5. API 草案

- `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`。
- `GET/POST /api/projects`、`GET/PATCH/DELETE /api/projects/:id`。
- `GET/POST /api/tasks`、`GET/PATCH/DELETE /api/tasks/:id`；按日期/状态筛选。重复任务的单次完成与跳过用显式端点，不误改整个规则。
- `GET/POST /api/records`、`GET/PATCH/DELETE /api/records/:id`；按日/范围查询。
- `GET /api/reviews?from=&to=`；服务器按实际记录汇总，预计快照只用于对比。
- `POST /api/imports/preview`、`POST /api/imports/:previewId/apply`；导入必须经预览及用户确认。`GET /api/exports` 提供含 schema/版本的完整个人数据导出。
- 请求/响应统一做运行时校验、分页和体积限制；服务端检查用户归属。错误中不回显密钥或个人内容。

## 6. 从 Vault 单向迁移（未来阶段，非本次执行）

1. 对原 Vault 做**仓库外**备份，用户明确确认导入对象；优先使用插件现有的 `lubi-data` JSON 导出作为输入。它不是完整 Vault 备份，也不是现有“追加任务”JSON 格式。
2. 在隔离环境、合成数据上验证解析：检查 envelope、任务 schema v14、日期、ID 唯一性、项目引用及记录关联；拒绝格式不匹配或过大文件。未知字段列清单，保留原导出文件副本或明确提示可能丢失；不静默丢弃。
3. 预览记录数、无效项、冲突项和引用关系；用户确认后在一个数据库事务里写入，保存批次与原始摘要。失败回滚，不写回 Vault；重新上传同一文件先提示已导入及差异。
4. 用抽样对照验证每日实际分钟、任务关联、项目数和重复发生日。跨午夜记录、待确认标记、历史预计快照和支出不能被简单求和或去重逻辑改变。
5. 首次导入后继续在原插件中编辑不会同步到 Web；后续增量导入须先定义冲突策略，不以重复整包导入冒充同步。

## 7. 安全、部署与验收

- 单用户仍需 HTTPS、强口令（Argon2id 或成熟框架实现）、HttpOnly/Secure/SameSite 会话 Cookie、CSRF 防护、登录限速、受保护的备份及最小权限数据库账户。密钥仅在服务器环境变量/秘密管理中；不进 Git、前端包或日志。
- 数据库首选 SQLite：单机单用户、读多写少时部署简单，数据库文件留在持久化数据目录，不放进构建产物或 Git。启用 WAL、`foreign_keys`、`busy_timeout`，由 API 服务串行化关键写事务；避免多台服务器共享数据库文件或把文件放在不可靠的网络盘。用户量、写并发或多机部署确实增长后再评估迁移 PostgreSQL。
- 部署首选单台服务器：API 服务同源提供 Web 静态资源，经 Caddy/Nginx 反代 HTTPS；可以直接用系统服务管理进程，不强制 Docker。数据库文件和备份目录只对服务账户开放。备份使用 SQLite 在线备份 API 或 `VACUUM INTO`/可靠快照，不直接复制正在 WAL 模式下写入的单个 `.db` 文件；定期在隔离目录做恢复演练。
- 仅在确认域名、系统与备份位置后写具体配置。
- 自动化测试：领域规则单测、API 授权/事务测试、浏览器核心流程；导入用合成 fixture，检查重导幂等、失败回滚、未知字段与历史预计。真实数据和生产上线需另行授权。
